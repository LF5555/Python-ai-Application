# セキュリティチェック（Streamlit + LLM + API アプリ用）

Streamlit で作った AI アプリの安全性を調べ、**セキュリティレポート**として報告するスキル。読み手はプログラミング初心者のことが多い。
目的は「考えられる問題を全部並べること」ではなく、「その使い方で本当に気にすべき問題を、根拠つきで、優先順位をつけて伝えること」。
個人用や小規模なアプリに、企業向けの対策（WAF、監査ログ、SOC など）を並べて不安にさせない。使い方に見合った対策だけを勧める。

## 守ること（理由つき）

- **`.env` と `.streamlit/secrets.toml` は開かない**（`cat`、`Get-Content`、Python から読むのも含む）。本物の API キーが入っていて、画面に出ただけで漏えいになるため。
  変数名は `.env.example` などのひな形やコードの `os.getenv(...)` / `st.secrets[...]` から調べ、値についてはユーザーに聞く。
- **秘密の値をレポートにも画面にも書かない**。スクリプトの出力も先頭 4 文字以外を伏せてある。それ以上を出さない。
- **チェック中はアプリのファイルを変えない**（作るのはレポートだけ）。修正は報告のあと、ユーザーが選んだ項目だけ。勝手に直すと、何が変わったか分からなくなるため。
- **確かめたことと推測を分ける**。コードを読んだ・コマンドを実行した結果は「確認済み」、それ以外は「未確認」と書く。脆弱性の有無を記憶だけで断定しない（情報が古い可能性がある）。
- **確認できなかった項目もレポートに書く**。黙って飛ばすと「問題なし」と誤解されるため。
- パッケージのインストールや外部への問い合わせ（`pip-audit` など）は、提案だけしてユーザーの許可を待つ。
- チェック対象は、ユーザーが指定したフォルダ（指定がなければ今のプロジェクトのフォルダ）の中だけ。

## 手順

### 1. 使い方を確認する（危険度の判断に必要）

同じコードでも、自分の PC だけで使うのか、インターネットに公開するのかで危険度が大きく変わる。
依頼文や `README.md` / `CLAUDE.md` から分からない点だけを、チェックを始める前に**まとめて 1 回**聞く:

1. 誰が使いますか？（自分だけ / 家族・同じ Wi-Fi の人 / 社内 / インターネットに公開）
2. ログインの仕組みを使っていますか？（使っているなら、パスワードなどの値は入っていますか）
3. AI サービスで、無料枠を超えると課金される設定（請求先の登録・有料プラン）にしていますか？

答えが得られない場合は「自分の PC だけで使っている」と仮定して進め、その仮定をレポートの「前提」に書く。

### 2. 調べる

`references/checklist.md` を読み、「0. 全体像をつかむ」から順に確認する。アプリに関係しない項目は「該当なし（理由）」とする。

付属のスクリプト（`<skill>` はこの `SKILL.md` があるフォルダ。パスは `"` で囲む）:
- `scripts/scan_secrets.py` — キーの直書き・git の履歴・`.env` / `secrets.toml` の追跡状態を、秘密のファイルを読まずに調べる。チェック対象のフォルダで実行する。
- `scripts/streamlit_config.py` — Streamlit のセキュリティ関連の設定の「実際の値」を表示する。そのアプリの仮想環境の Python で `-I` を付けて実行する。

コードは必ずその時点のものを読む。チェックリストの記述と実際のコードやライブラリの動作が違ったら、実際に確かめた方を優先する。
ユーザーが特定の点（例: 「API キーだけ」）を聞いた場合は、その分野を中心に調べ、他の分野は「高」の問題だけ短く触れる。

### 3. セキュリティレポートを作る

チェック対象のプロジェクトのフォルダ直下に `security-report-YYYY-MM-DD.md`（今日の日付）として保存する。
同じ名前のファイルがあれば上書きせず、`-2`、`-3` を付けた名前にする。
レポートには弱点の場所が書かれるので、公開するリポジトリには含めないよう、画面での報告で一言添える（`.gitignore` への追加は提案だけにする）。

レポートは次のテンプレートに沿って書く:

```markdown
# セキュリティレポート: <アプリ名>

- 実施日: YYYY-MM-DD
- 対象: <フォルダのパス>（<入口のファイル>）
- 構成: <例: Streamlit 1.xx / Gemini（REST）/ Cloudflare Workers AI / DB なし>
- 前提: <手順 1 で確認した使い方。仮定した場合は「〜と仮定」>

## 1. まとめ

<2〜4 行。一番気にすべきことを最初に。全体の評価をひと言で>

| 危険度 | 件数 |
|--------|------|
| 高 | n |
| 中 | n |
| 低 | n |
| 情報 | n |

## 2. 見つかった問題

| # | 危険度 | 分類 | 内容 | 場所 |
|---|--------|------|------|------|
| 1 | 高 | 公開範囲 | …… | `app.py:60` |

### 2-1. <問題の名前>【高】

- **何が起きるか**: <具体的な被害を 1〜2 文。例:「同じ Wi-Fi の人がアプリを開き、あなたの API キーで AI を使えます」>
- **起きる条件**: <例:「認証なしで LAN に公開しているとき」>
- **根拠**: <読んだコード（ファイル:行）・実行したコマンドとその結果。確認済み / 未確認を明記>
- **直し方**: <何をどう変えるか。専門用語にはひと言説明を添える。コード例は短く>
- **ユーザー自身の作業**: <あれば。例: API キーの作り直し、予算アラートの設定>

## 3. 問題なしと確認できた項目

- <例: `.env` は git に一度も入っていない（`scan_secrets.py` で確認）>

## 4. 該当なしの項目

- <例: ファイルのアップロード機能はないため、G は対象外>

## 5. 確認できなかった項目

- <例: パッケージの既知の脆弱性（`pip-audit` が入っていないため未確認）>

## 6. 次にやること

1. <優先度の高い順に。直す項目、ユーザー自身が行う作業など>
```

危険度の目安:
- **高**: 今の使い方で、キーの漏えい・他人による利用・請求・データの流出が実際に起こりうる
- **中**: 使い方が変わる（公開する、公衆 Wi-Fi で起動する、他人に使わせる）と起こりうる
- **低**: 起こる可能性や被害が小さい。余裕があれば直す
- **情報**: 問題ではないが知っておくとよいこと

問題が 1 つもなければ、無理に作らず「大きな問題は見つかりませんでした」と書き、確認した範囲を示す。

### 4. 画面で報告する

レポートの全文は貼らず、次の順で短く伝える:
1. やったこと（調べた範囲、作ったレポートのフルパス）
2. 確認した結果（危険度ごとの件数と、「高」「中」の問題の一覧を 1 行ずつ）
3. ユーザーが次にやること（レポートを開いて読む、直したい番号を教える、など）

最後に「直したい番号を教えてください（例: 1 と 3）」と聞く。返事が来るまでアプリのファイルは何も変えない。

### 5. 許可が出た項目だけ直す

1. 触るファイルを先に伝える。新しいファイル（例: `.streamlit/config.toml`）を作る場合もそう伝える。
2. 編集する直前にファイルを読み直す。前に読んだ内容と違ったら（別のセッションが変えた可能性）、上書きせずに報告する。
3. 既存の書き方に合わせて最小限だけ直す。頼まれていない「ついでの修正」はしない。気づいた別の問題は報告だけにする。
4. 動作確認する。プロジェクトの `CLAUDE.md` に確認方法があればそれに従う。なければ `streamlit.testing.v1.AppTest` で画面が例外なく表示されるかを確かめる（`AppTest.from_file()` には絶対パスを渡す）。
   有料・回数制限のある API を呼ぶ確認は、短い入力で 1 回までにし、できればモックで済ませる。
5. 「やったこと → 確認した結果 → ユーザーが次にやること」の順で報告する。反映方法も書く（`.py` はブラウザの「Rerun」かページの再読み込み、`.streamlit/config.toml` や依存パッケージの変更はターミナルで Ctrl + C を押して再起動）。
6. レポートの該当項目に「対応済み（YYYY-MM-DD）」と追記する。
7. git 管理されていれば、コミットしてよいか聞く。`git push` はユーザーの確認なしにしない。

API キーの作り直し、予算アラートの設定、パスワードの変更、ホスティング側の公開設定など、ユーザー自身にしかできない作業は、手順を番号付きで書いて頼む。
